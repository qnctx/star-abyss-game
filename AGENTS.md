# Project collaboration rules

- Every new or reworked 3D asset must start with a generated concept/reference image. Build the corresponding 3D model from that image, then integrate it into the game and visually verify it. Do not deliver primitive placeholder geometry as finished art.
- For every future new or redesigned character/creature action, martial skill, and effect, first generate detailed image breakdowns of that specific design, then build the 3D animation/effect from them. A generic character picture is not an action breakdown. Show key poses and timing, support/weight transfer, hand/foot paths, anticipation, release/contact, recovery, and effect origin/trajectory/hit/miss/interruption/dissipation as applicable. Review the images for anatomical and phase consistency before production; retain the image-to-asset mapping and verify the final skinned result and effects in Godot at normal speed. Do not substitute parameter-only animation tweaks or procedural placeholder effects for this design workflow.
- The current development mainline is `godot/project.godot`. `src/` is the legacy survival/tower-defense Godot project; `playable/` is the historical browser game and migration reference. Do not treat either as the current product or require ongoing cross-engine feature parity.
- Preserve the six-kilometre lunar world, character, sky, vehicles, investigation and compatible native saves in the current Godot game while replacing art. Historical browser code may be retired after source assets, migration dependencies and recoverable backups are verified; do not delete shared assets or evidence merely because their directory originated in the browser project.
- The user prefers a controller coordinating development tasks with separate independent verification tasks.
- Preserve unrelated dirty worktree changes; update relevant project documentation and report concrete verification steps for each feature slice.
- Prefer cmd or Bash; do not use PowerShell by default.
- UI must keep Chinese text readable and buttons visible and clickable.
- Billable generation approval is scoped to the approved batch; the image-first workflow preference does not grant unlimited spending.
