# AI 开发自我反思规则 (GLM 5.2 + Trae)

> 版本：v1.0
> 适用：GLM 5.2 在 Trae IDE 中进行 Godot / GDScript 游戏开发
> 目的：最大化发挥 AI 编程能力，确保代码质量，减少反复修正

---

## 一、核心原则

### 1.1 三思而后行
- **先理解，再动手**：任何代码修改前，必须先读相关文件、理解现有架构
- **先规划，再编码**：复杂任务必须用 TodoWrite 拆解步骤
- **先验证，再交付**：完成后必须运行测试、检查诊断

### 1.2 最小惊讶原则
- 遵循项目现有代码风格和命名约定
- 优先修改现有文件，而非新建文件
- 新增功能必须与现有架构模式一致

### 1.3 可测试性优先
- 每个新功能必须考虑如何测试
- 优先编写可独立测试的纯函数/模块
- 修改代码前先看现有测试，确保不破坏

## 二、任务执行五阶段反思流程

### 阶段 1：需求澄清与拆解
**执行前自问：**
- [ ] 用户需求是否明确？有没有歧义？
- [ ] 需求范围是否清晰？做什么 / 不做什么？
- [ ] 是否需要向用户确认关键点？
- [ ] 这个任务涉及哪些文件/模块？
- [ ] 任务复杂度如何？是否需要 Todo 拆解？

**判断标准：**
- 能在 2 个工具调用内完成的简单任务 → 直接执行
- 涉及 3+ 文件或多步骤 → 必须用 TodoWrite 规划
- 需求模糊或有多种实现方式 → 必须用 AskUserQuestion 确认

### 阶段 2：上下文收集与理解
**执行前自问：**
- [ ] 相关的代码文件都读过了吗？
- [ ] 理解现有数据结构和信号流吗？
- [ ] 有没有类似功能的实现可以参考？
- [ ] 项目的编码规范是什么？（命名、缩进、注释等）
- [ ] 这个改动会影响哪些其他系统？

**必做动作：**
1. 读取 [CLAUDE.md](../src/CLAUDE.md) 了解项目架构规则
2. 读取 [CONTEXT.md](../src/CONTEXT.md) 了解领域模型
3. 搜索相关代码，至少看 2-3 个类似实现
4. 查看现有测试文件，了解测试模式

### 阶段 3：方案设计与规划
**设计时自问：**
- [ ] 有没有更简单的实现方式？
- [ ] 这个方案是否符合现有架构模式？
- [ ] 会不会引入不必要的复杂度？
- [ ] 性能方面有没有问题？
- [ ] 边界情况考虑了吗？（空值、错误输入、极端情况）

**方案选择原则：**
1. **优先复用**：能用现有机制就不造新轮子
2. **最小改动**：用最少的代码变更实现需求
3. **数据驱动**：优先用数据/配置而非硬编码逻辑
4. **信号解耦**：模块间用 Godot signals 通信，避免直接引用

### 阶段 4：编码实现
**编码时自问：**
- [ ] 变量名/函数名是否清晰？
- [ ] 有没有遵循项目的命名约定？
- [ ] 代码逻辑是否容易理解？
- [ ] 有没有必要的注释？（注释解释"为什么"，不是"做什么"）
- [ ] 有没有复制粘贴的重复代码？
- [ ] 错误处理到位了吗？

**GDScript 编码规范（本项目）：**
- 变量/函数：`snake_case`
- 类名：`PascalCase`
- 信号名：`snake_case`
- 注释用英文，UI 文本用中文
- 优先使用 `@onready` 而非 `_ready()` 中的变量赋值
- 信号定义放在文件顶部
- 使用 `class_name` 定义可复用的节点类型

### 阶段 5：验证与交付
**交付前自问：**
- [ ] 测试跑过了吗？
- [ ] 有没有 lint/type 错误？
- [ ] 新增功能有测试覆盖吗？
- [ ] 文档更新了吗？（如果需要）
- [ ] 相关的上下文文档（CONTEXT.md）更新了吗？
- [ ] 进度文档（PROGRESS.md）更新了吗？

**验证清单：**
1. 运行测试：`test_runner.gd` 和 `test_standalone.gd`
2. 主场景启动测试：`--quit-after 2`
3. Git 检查：`git diff --check`
4. 手动测试步骤（如果有 UI/交互变更）
5. 更新相关文档

## 三、常见错误自检清单

### 3.1 Godot/GDScript 常见坑
- [ ] 信号连接写对了吗？参数数量和类型匹配吗？
- [ ] `queue_free()` vs `free()` 用对了吗？（信号回调中用 queue_free）
- [ ] `@onready` 变量在 `_ready()` 之前访问了吗？
- [ ] 节点路径 `$NodeName` 正确吗？
- [ ] 组名（group）拼写一致吗？
- [ ] 元数据（meta）的 key 对得上吗？
- [ ] Autoload 单例的名字对吗？通过 `/root/Name` 访问了吗？

### 3.2 逻辑错误
- [ ] 边界条件处理了吗？（0、空数组、null、最大值）
- [ ] 除以零的可能？
- [ ] 计时器/定时器的 delta 时间累积正确吗？
- [ ] 状态机的状态转换完整吗？有没有遗漏的状态？
- [ ] 事件触发顺序有没有问题？

### 3.3 性能问题
- [ ] `_process()` 里有没有昂贵的操作？（每帧查找节点、大量计算）
- [ ] 有没有不必要的 `get_node()` / `$` 调用（应该缓存）？
- [ ] 大量实例化时有没有考虑对象池？
- [ ] 信号连接有没有重复连接？

## 四、Trae 工具使用最佳实践

### 4.1 工具选择策略
| 任务类型 | 推荐工具 | 注意事项 |
|---------|---------|---------|
| 查找代码 | `SearchCodebase` / `Grep` | 跨模块搜索用 SearchCodebase，精确匹配用 Grep |
| 读取文件 | `Read` | 大文件用 offset/limit 分段读 |
| 找文件 | `Glob` / `LS` | 按名称模式找用 Glob，看目录用 LS |
| 修改代码 | `Edit` | 优先用 Edit 而非 Write |
| 新建文件 | `Write` | 尽量避免，除非确实需要 |
| 运行命令 | `RunCommand` | 短命令用 blocking，服务器用 non-blocking |
| 多步骤任务 | `TodoWrite` | 3 步以上必须用 |
| 需求不清 | `AskUserQuestion` | 不要猜，直接问 |
| 独立子任务 | `general_purpose_task` | 任务独立且不需要共享上下文时用 |

### 4.2 搜索策略
1. **先用 SearchCodebase**：自然语言描述，获取相关代码片段
2. **再用 Grep 精确定位**：精确的变量名/函数名/字符串
3. **读取完整文件**：理解上下文，不要只看片段
4. **追溯调用关系**：找调用方和被调用方

### 4.3 Edit vs Write
- **90% 的情况用 Edit**：修改现有文件的特定部分
- **只有全新文件才用 Write**：并且确认是必要的
- **大段重写慎用 Write**：先用 Read 确认内容，再考虑用 Edit 分步修改

## 五、自我修正循环

### 5.1 遇到错误时的处理流程
```
发现错误
   ↓
理解错误信息（仔细读报错）
   ↓
定位出错的代码位置
   ↓
分析根本原因（不是表面现象）
   ↓
思考修复方案（至少想 2 种）
   ↓
选择最小改动方案
   ↓
实施修复
   ↓
验证修复（跑测试）
   ↓
反思：为什么会犯这个错？以后怎么避免？
```

### 5.2 反复失败时的应对
如果同一个问题改了 2 次还不对：
1. **停下来重新理解**：可能你的理解从根本上就是错的
2. **从头读相关代码**：不要盯着改的那几行，看整个上下文
3. **搜索类似实现**：项目里有没有做过类似的事？
4. **考虑换个思路**：原来的方案可能走不通，换个角度
5. **必要时问用户**：承认卡住了，寻求澄清或建议

## 六、代码质量标准

### 6.1 可读性
- 函数名应该描述做什么，不是怎么做到的
- 函数应该尽量短，一个函数只做一件事
- 嵌套层级不超过 3 层
- 避免魔法数字，用常量或枚举

### 6.2 可维护性
- 模块间低耦合，模块内高内聚
- 优先用信号（signals）而非直接引用
- 数据和逻辑分离
- 配置数据尽量导出（`@export`）或用资源文件

### 6.3 一致性
- 新代码必须和旧代码风格一致
- 命名模式要统一（比如 `_on_xxx_signal` 表示信号处理函数）
- 缩进、空行、括号风格统一

## 七、项目特定规则

### 7.1 本项目架构规则
- 每个系统是独立的 GDScript 文件，通过 signals 通信
- 使用 Godot 内置节点（CharacterBody3D, Area3D 等）
- 全局管理器用 Autoload singleton
- UI 用 Control 节点 + signals

### 7.2 测试要求
- 每个新功能 / 修复都要有对应的测试
- 测试用例命名要清晰描述测试场景
- 测试必须同时覆盖正常情况和边界情况
- 运行 `test_runner.gd`（集成测试）和 `test_standalone.gd`（独立测试）

### 7.3 文档更新
- 新增系统/功能 → 更新 [CONTEXT.md](../src/CONTEXT.md)
- 重要进度 → 更新 [PROGRESS.md](../PROGRESS.md)
- UI/交互变更 → 更新 [TEST_PLAN.md](TEST_PLAN.md)

## 八、每日工作开始检查清单

每次开始新任务前，快速过一遍：

1. [ ] 我理解用户要什么了吗？
2. [ ] 我知道改哪些文件吗？
3. [ ] 我读过相关的现有代码了吗？
4. [ ] 我知道项目的规范和模式吗？
5. [ ] 这个任务需要拆解成 Todo 吗？
6. [ ] 我打算怎么验证我的改动？

---

## 九、交付前最终检查清单

提交/交付前必须确认：

1. [ ] 所有测试通过
2. [ ] 没有 lint / type 错误
3. [ ] 代码风格符合项目规范
4. [ ] 没有无用的注释掉的代码
5. [ ] 没有硬编码的调试语句（print 等，除非确实需要）
6. [ ] 相关文档已更新
7. [ ] 我自己 review 过一遍改动
